# Implementation status

## Native routing update

The repository now contains the automatic native broker, durable host reservations, pinned single-use launchers, GitHub identity verification, actual source-runner assignment checks and restart/cancellation reconciliation. The dashboard starts at Repositories, loads actual workflow jobs and dependencies, and lets one admin save ordered providers and machine overrides at workflow or job level. It no longer presents command recipes, a synthetic routing preview or a test-group planner as the main workflow interface.

GitHub usage attribution prevents completed worker minutes from being subtracted twice when the billing report identifies the worker repository. Missing attribution retains conservative accounting. Native and previous recipe runs share one capacity ledger. All ten Standard/Premium x64 Ubicloud sizes are selectable with configured rates; explicit native family choices are checked before JIT delivery. Paid rates remain estimates and automatic Premium must be disabled in Ubicloud for a Standard choice.

These implementation details are covered by service, bootstrap and UI regression tests. The previously recorded live evidence below remains historical: a second account's ready native launcher, automatic private cross-account execution and matched speed benchmarks still require live acceptance. General Wisbid runner adoption is a separate reviewable workflow change; dedicated production builders and release protections are retained. Automatic Quality sharding is the next experiment, not an implemented speedup.

## Scope and limits

Normal startup has no example accounts, fabricated runs or sample timings. Synthetic accounts and credentials exist only in automated test fixtures. The separate fixture server requires the test environment and loopback; it cannot dispatch or modify provider connections.

The source owner defines approved command recipes. Each named workload is independent, with no implicit dependency graph. Several workloads on the same source repository can run concurrently across separately consenting owners. Manual runs pin an exact commit; optional signed default-branch pushes enqueue the configured workloads idempotently. Pull-request automation is not enabled.

The controller records intent before external mutations. A lost dispatch response is reconciled; it is never blindly retried or routed elsewhere. Unknown acceptance keeps its capacity reserved. A failed application command stays failed. Cancellation and publication have durable states so cancellation cannot race into a false success. Provider identity mismatches fail closed and retain uncertain capacity for investigation.

The worker launcher, source revision and recipe are snapshotted per run. Its one-use GitHub identity must match the immutable repository IDs, approved worker revision, tag, accepted run ID and first attempt. The server revokes a fresh source-only read token before project commands run. The audit is uploaded as an immutable artifact before project code and is verified independently alongside GitHub's job and step results. Callback responses and project output cannot report success.

Account usage must be current for the UTC month and verified within 15 minutes. Queued work refreshes eligible connections roughly every five minutes, with retry backoff. Unsupported minute SKUs fail closed. The owner confirms their included allowance; this API does not provide a complete remaining-allowance contract. Other workflows can spend concurrently. Retain GitHub spending controls and a reserve. Local completed usage remains counted conservatively until billing settlement is proved, which can reduce usable capacity temporarily.

BuildFerry is a single-company installation with one administrator. Optional environment-variable username/password sign-in separates dashboard administration from GitHub account authorization. The administrator can manage every connected account's limits and worker project selections; contributors finish on a simple connected screen. There are no organization roles, delegation toggles or tenant controls.

New App manifests request Repository creation write in addition to Plan and Metadata read, plus Actions, Contents, Workflows and Checks write. Automatic private worker creation verifies the account identity, records a durable creation marker, reconciles lost responses and refuses unrelated existing repositories. Existing Apps need the added permission approved before this path can work live. Tokens issued for checkout are narrowed to one source repository and Contents read only; worker dispatch tokens are narrowed to one worker repository. No administration, branch bypass, deployments or production secrets are requested.

Ubicloud now has an editable default machine, with 2 CPUs / 8 GB selected for new connections. Workload and individual-run choices override that default. Each additional size requires an entered rate. There is no automatic upsizing or silent replacement of an unavailable machine. Changing settings preserves existing reservations and monthly usage. The live benchmark configuration and spending cap are not changed by deploying these controls.
